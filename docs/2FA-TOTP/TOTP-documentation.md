# Two-Factor Authentication (TOTP) — Technical Documentation

## 1. Overview

The application supports Two-Factor Authentication (2FA) using **Time-Based One-Time Passwords (TOTP)**.

TOTP adds a second verification step to login. Instead of relying only on an email and password, users must also provide a temporary six-digit code generated by an authenticator application.

The code changes automatically every 30 seconds.

## 2. How It Works

The implementation has two main flows:

- Enabling MFA from the user's profile.
- Authenticating with MFA during login.

### 2.1 Enabling MFA

1. The authenticated user opens their account settings.
2. The frontend requests a TOTP setup from the backend.
3. The backend generates a secret and returns a provisioning URI.
4. The frontend generates a QR code locally from that URI.
5. The user scans the QR code using an authenticator application.
6. The application generates a six-digit code.
7. The user enters the code in the frontend.
8. The backend validates the code and enables MFA for the account.

After successful confirmation, MFA is enabled.

**Important:** The QR code is generated locally in the frontend. The provisioning URI contains the TOTP secret and must never be sent to an external QR-generation service.

### 2.2 Login With MFA

When MFA is disabled:

1. The user submits their email and password.
2. The backend validates the credentials.
3. The backend returns the access token and user information.
4. The frontend stores the access token and completes authentication.

When MFA is enabled:

1. The user submits their email and password.
2. The backend validates the credentials.
3. Instead of issuing a normal authenticated session, the backend returns an MFA challenge.
4. The frontend displays the six-digit verification form.
5. The user enters the code generated by their authenticator.
6. The frontend sends the challenge token and code to the backend.
7. The backend validates the challenge and TOTP code.
8. If valid, the backend returns the access token and user information.
9. The frontend stores the access token and completes authentication.

The challenge token is not an access token. It must not be used to authorize normal API requests.

## 3. Backend API

All endpoints below are relative to `/api`.

| Method | Endpoint                     | Purpose                               |
| ------ | ---------------------------- | ------------------------------------- |
| POST   | `/auth/login`                | Authenticate using email and password |
| POST   | `/auth/mfa/verify`           | Verify the TOTP challenge             |
| GET    | `/users/me/mfa/status`       | Retrieve MFA status                   |
| POST   | `/users/me/mfa/totp/setup`   | Generate TOTP setup information       |
| POST   | `/users/me/mfa/totp/confirm` | Confirm the authenticator code        |

### Login response

The authentication response contains:

- `accessToken`: issued after successful authentication.
- `user`: authenticated user information.
- `mfaRequired`: indicates whether a second verification step is required.
- `challengeToken`: temporary token used to complete MFA verification.

### MFA verification request

```json
{
  "challengeToken": "temporary-challenge-token",
  "code": "123456"
}
```

### MFA setup response

```json
{
  "provisioningUri": "otpauth://totp/..."
}
```

### MFA confirmation request

```json
{
  "code": "123456"
}
```

### MFA status response

```json
{
  "enabled": true
}
```

## 4. Frontend Implementation

The Angular frontend is responsible for presenting the MFA flow and communicating with the backend.

### AuthService

Handles:

- Normal login.
- MFA verification.
- Access-token storage after successful authentication.

The access token is only stored after the complete authentication process. An MFA challenge must never be treated as a successful login.

### UserService

Handles:

- Retrieving MFA status.
- Requesting TOTP setup.
- Confirming the authenticator code.

### Login Component

Maintains two authentication states:

- Credentials form.
- MFA verification form.

After receiving an MFA challenge, it displays the verification form instead of navigating to the application.

### Profile Component

Provides the MFA settings interface:

- Displays whether MFA is enabled.
- Starts TOTP setup.
- Displays the QR code.
- Allows manual provisioning URI access.
- Accepts and submits the six-digit confirmation code.

## 5. Security Considerations

- Never store the challenge token as an access token.
- Never expose the TOTP secret in application logs.
- Do not send provisioning URIs to third-party QR-generation services.
- Validate the six-digit code on the backend.
- Protect MFA management endpoints with authentication.
- Use HTTPS in production.
- Apply appropriate expiration and single-use rules to MFA challenge tokens.
- Protect TOTP secrets at rest.

## 6. Current Scope

The implemented feature covers:

- TOTP enrollment.
- QR-code provisioning.
- TOTP confirmation.
- MFA status retrieval.
- Password-based login with an MFA challenge.
- MFA challenge verification.
- Access-token issuance after successful verification.

**MFA disabling is not included** because the current backend API does not expose a disable endpoint.

## 7. Recommended Documentation

These are the most useful references for understanding and maintaining the feature:

1. **RFC 6238 — TOTP: Time-Based One-Time Password Algorithm**  
   https://datatracker.ietf.org/doc/html/rfc6238  
   The technical standard defining how TOTP codes are generated and validated.

2. **RFC 4226 — HOTP: An HMAC-Based One-Time Password Algorithm**  
   https://datatracker.ietf.org/doc/html/rfc4226  
   Explains the underlying one-time password algorithm used by TOTP.

3. **OWASP Multifactor Authentication Cheat Sheet**  
   https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html  
   Practical security recommendations for implementing and maintaining MFA.

4. **Google Authenticator — Set up Authenticator**  
   https://support.google.com/accounts/answer/1066447  
   Explains how users enroll an authenticator application.

---

**In short:** Password authentication establishes the first factor. TOTP verification establishes the second. Only after both succeed does the backend issue the normal access token.
